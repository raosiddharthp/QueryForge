# ADR-006: Project-scoped budget guard over an account-level, billing-data-reactive kill switch

**Status:** Revised (original: Pub/Sub-notified Cloud Function kill switch, project-scoped)

## Context

The common pattern for a hard cost cap is a Cloud Billing Budget that triggers a Pub/Sub
notification to a Cloud Function once a spend threshold is crossed. QueryForge's project shares a
$10 billing account with three other apps, so the first revision of this ADR scoped that pattern
to the project only — never the account — so a cap breach here could never take down the sibling
apps.

That scoping was correct, but building it surfaced a more fundamental problem: **Google's own
billing data lags by "at least 24 hours"** per its published documentation. A reactive,
billing-data-driven trigger — whether it's a Pub/Sub push or a Cloud Scheduler poll of billing
exports — cannot enforce a $0.01 cap in real time. By the time any billing-data-reactive
mechanism would detect an overspend, the overspend has already happened. For a $10-account,
four-app blast radius, "detected a day later" is not the same guarantee as "never happened."

## Decision

Self-enforce the cap in application code instead. `build/service/budget_guard.py` tracks
estimated Gemini spend in a Firestore document, using a transactional read-check-write on every
call: before any Gemini request fires, it checks the running total for the current month against
the $0.01 cap; after the call returns, it records the estimated cost from the response's token
usage. Zero dependency on GCP's billing pipeline, zero lag.

The Cloud Billing Budget from the original ADR-006 (`infra/main.tf`,
`google_billing_budget.queryforge_secondary_cap`) is kept, still project-scoped — but now as an
independent **secondary** tripwire: defense in depth in case `budget_guard.py` itself has a bug,
not the primary enforcement mechanism.

## Consequences

The cap is enforced with sub-second latency instead of a 24-hour-plus lag, at the cost of one
extra Firestore transaction per Gemini call (well inside the Always-Free daily write quota at
demo volume). The estimate uses published per-token pricing (`PRICING` dict in
`budget_guard.py`) rather than actual billed cost, so it can drift slightly from GCP's own
invoice — acceptable for a hard-stop guard, not acceptable if this were the only cost record kept
(it isn't; Firestore's `query_logs` collection and Cloud Billing's own reports both exist
independently).

## Alternatives

- **Account-level "disable billing" kill switch** — rejected in the original ADR. A QueryForge
  cost spike would take down three unrelated apps as collateral damage.
- **Project-scoped Pub/Sub + Cloud Function kill switch (original decision)** — superseded here.
  Correct in scope, but the billing-data lag makes it too slow to be the primary safeguard for a
  cap this small. Retained as the secondary tripwire described above.
