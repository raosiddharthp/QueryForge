# ADR-002: Firestore Vector Search over ChromaDB or Vertex AI Vector Search

**Status:** Accepted

## Context

The retrieval layer needs a persistent vector index. Cloud Run's local disk is ephemeral, so a
self-hosted ChromaDB instance loses its index on every cold start unless paired with a separate
persistent volume — adding cost and complexity. Vertex AI Vector Search is Google-native but has
no Always-Free tier; its cheapest deployed index runs continuously and accrues an hourly charge
regardless of query volume.

## Decision

Use Firestore (Native mode) with vector search for both the dense index and the query/config
store. It is Google-native, persists across cold starts, and its Always-Free daily allotment
(1 GiB storage, 50K reads / 20K writes per day) comfortably covers a portfolio-scale demo corpus.

## Consequences

Corpus size for the zero-cost demo is bounded by Firestore's Always-Free storage (see the design
doc's Limitations section). Production graduation to Vertex AI Vector Search is a config change,
not a rewrite — `retrieval.py`'s `dense_retrieve()` is the only function that would need to swap
its backing call.

## Alternatives

- **Self-hosted ChromaDB** — rejected. No free persistent disk on Cloud Run; requires a separate
  Compute Engine VM or Filestore volume, both outside the Always-Free tier.
- **Vertex AI Vector Search** — rejected for the MVP. Google-native, but the deployed index has
  an always-on hourly cost with no free tier; incompatible with a $0.01 cap. Documented as the
  production upgrade path.
